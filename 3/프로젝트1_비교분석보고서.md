# [프로젝트 1] 자동화 도구 비교 구현 — Make vs n8n

> 작성 상태: Make · n8n 구현 완료. 본문 📷 표시 위치에 실제 스크린샷을 삽입하고 마스킹을 확인할 것.

---

## 1. 개요

### 1.1 구현 워크플로우

**"만족도 조사 자동 분류 및 알림"**

Tally 설문 폼 제출(만족도 1~5점) → 점수 기준 조건 분기 → 불만족(3점 이하) 응답은 Notion 기록 + Discord 즉시 알림, 만족(4점 이상) 응답은 Notion 기록만 수행하는 워크플로우.

```
Tally 폼 제출 (실제 이벤트 트리거)
        │
        ▼
   Webhook 수신
        │
        ▼
   조건 분기 (만족도 기준)
        │
   ┌────┴─────────────┐
   ▼                  ▼
[3점 이하: 불만족]   [4점 이상: 만족]
   │                  │
   ▼                  ▼
Notion 기록          Notion 기록
   │               (결과: 정상)
   ▼
Discord 알림
(결과: 불만족 알림)
```

### 1.2 시나리오 선정 이유

- 처음에는 "점수 80점 기준 합격/불합격 분류"로 시작했으나, 웹훅 URL을 수동으로 호출하는 테스트 방식은 트리거 이후만 자동일 뿐 **트리거 자체가 사람 손에 의존**한다는 한계를 발견함
- 이에 실제 이벤트 소스(설문 폼 제출)가 트리거가 되도록 재설계 — 사람의 개입 없이 "폼 제출 → 분류 → 기록 → 알림"이 전부 자동으로 이루어짐
- 불만족 응답만 선별해 즉시 알리는 구조는 실무 CS(고객 응대) 현장에서 실제로 쓰이는 패턴으로, 자동화의 목적(모든 응답을 사람이 확인하는 대신 문제 응답만 즉시 통보)이 명확함

### 1.3 요구사항 충족 매핑

| 과제 요구사항 | 구현 내용 |
|---|---|
| Trigger 1개 이상 | Tally 폼 제출 → Webhook 수신 |
| Action 2개 이상 | Notion 데이터베이스 기록, Discord 웹훅 알림 |
| 조건 분기 1개 이상 | 만족도 ≤ 3 / ≥ 4 분기 (Make: Router, n8n: IF 노드) |
| 각 분기 경로 1회 이상 실행 확인 | 만족도 2 제출(불만족 경로), 만족도 5 제출(만족 경로) 각각 실행 검증 완료 |
| 서로 다른 2개 이상 도구 | Make(완료), n8n(예정) |
| 동일한 워크플로우 구조 | 동일 구조로 구현 |

### 1.4 사용 도구 및 스택

| 역할 | 도구 | 비고 |
|---|---|---|
| 폼(이벤트 소스) | Tally | 무료 플랜, 웹훅 기본 지원 |
| 자동화 도구 1 | Make | 무료 플랜 (월 1,000 Ops) |
| 자동화 도구 2 | n8n | Docker 셀프호스팅 (docker.n8n.io/n8nio/n8n, 무료) |
| 데이터 기록 | Notion | 데이터베이스 (이름/만족도/결과/의견/타임스탬프) |
| 알림 | Discord | 채널 웹훅 |

## 2. Make 구현

### 2.1 워크플로우 구성

```
Webhooks(Custom webhook) → Router → [만족도 ≤ 3] → Notion(Create a Data Source Item) → HTTP(Discord POST)

```

### 2.2 구현 과정 요약

1. **Tally 폼 생성** — 이름(Short answer), 만족도(Linear scale 1~5), 의견(Long answer, 선택) 3개 필드로 구성 후 발행
2. **Tally → Make 웹훅 연결** — Tally의 Integrations 탭에서 Webhooks 연동에 Make의 Custom Webhook URL을 등록. 폼 제출 즉시 Make로 데이터가 전송됨
3. **웹훅 데이터 구조 학습** — 테스트 응답 1건을 제출해 Make가 Tally의 데이터 구조를 학습하도록 함 ("Detect new values")
4. **Router + 필터 설정** — 만족도 값 기준으로 2개 경로 분기. 필터 조건에 **Numeric operators** 사용
5. **Notion 모듈 설정** — "Create a Data Source Item" 모듈로 데이터베이스에 행 추가. 이름/만족도/의견은 웹훅 데이터 매핑, 결과는 경로별 고정값(불만족 알림/정상), 타임스탬프는 `now` 함수
6. **Discord 알림** — 불만족 경로에만 HTTP 모듈(POST, application/json)로 Discord 웹훅 호출
7. **분기별 실행 검증** — 만족도 2 제출(불만족 경로: 기록+알림 확인), 만족도 5 제출(만족 경로: 기록만, 알림 없음 확인), Scheduling ON 상태에서 무개입 자동 실행 확인

### 2.4 구현 중 겪은 이슈와 해결 (Make)

| 이슈 | 원인 | 해결 |
|---|---|---|
| Notion 모듈이 두 종류로 검색됨 | Notion API 용어 변경(Database → Data Source)으로 신구 모듈 공존 | **(Legacy)가 붙지 않은 "Create a Data Source Item"** 선택 |
| `path.data_source_id should be a valid uuid` 오류 | Data Source ID 칸에 ID 대신 필드 매핑을 입력 | Notion DB URL의 32자리 ID를 직접 입력 (또는 ID Finder 사용) |
| 타임스탬프 `Value is not a valid date` 오류 | `now`를 일반 텍스트로 타이핑 | 매핑 패널의 Date/Time 탭에서 **now 함수 태그**로 삽입 |
| 필터 연산자 함정 | Text 연산자로 숫자 비교 시 문자열 비교가 됨 (`"9" > "80"`이 참) | **Numeric operators** 그룹의 연산자 사용 |
| Tally 연동 후 기존 매핑 무효화 | Tally는 `data.fields[]` 배열 구조로 전송 → 기존 `name`/`score` 평면 구조와 다름 | 웹훅 재학습 후 `data.fields[n].value` 인덱스 방식으로 전 모듈 재매핑 |

### 2.5 Make 사용 소감 (장단점 초안)

**장점**
- 시각적 캔버스에서 데이터 흐름이 직관적으로 보임 — Router 분기 구조가 그림 그대로 이해됨
- Notion, Discord 등 연결이 OAuth 클릭 몇 번으로 끝남 (API 키 발급 불필요)
- 웹훅 대기열(queue) 관리, 실행 History 등 운영 편의 기능이 잘 갖춰짐
- 모듈이 데이터 구조를 자동 학습("Detect new values")해 매핑 패널에서 클릭만으로 매핑 가능

**단점 / 주의점**
- 동일 기능의 신구 모듈(Legacy)이 공존해 초심자가 헷갈리기 쉬움
- UI가 자주 업데이트되어 온라인 자료와 화면이 다른 경우가 있었음
- 무료 플랜 월 1,000 Ops 제한 — 폴링형 트리거를 쓰면 응답이 없어도 Ops가 소모됨 (웹훅형 트리거로 회피 가능)
- 매핑을 텍스트로 직접 타이핑하면 안 되고 반드시 태그로 삽입해야 하는 규칙이 처음엔 낯설음

## 3. n8n 구현

### 3.1 환경 구축

- n8n을 Docker 컨테이너로 셀프호스팅했다. (Docker 환경은 사전에 구축되어 있었음)
  - 실행 명령: `docker run -it --rm --name n8n -p 5678:5678 -v n8n_data:/home/node/.n8n docker.n8n.io/n8nio/n8n`
  - `http://localhost:5678` 접속 후 로컬 관리자 계정 생성
- **Notion 연동을 위한 API 통합 수동 생성** (Make와의 핵심 차이):
  1. notion.so/my-integrations에서 신규 연결 생성 (이름 `n8n`, 인증 방법 "액세스 토큰", 워크스페이스 지정)
  2. 발급된 Internal Integration Secret(`ntn_...`)을 복사
  3. Notion 대상 DB 페이지 → `···` → 연결(Connections)에서 `n8n` 통합을 명시적으로 추가

> Make는 Notion 연결이 OAuth 클릭 몇 번으로 끝났지만, 셀프호스팅 n8n은 위와 같이 API 통합 생성 → 시크릿 발급 → 페이지 접근 권한 수동 부여의 3단계를 직접 거쳐야 했다. 이 차이가 설정 난이도 비교의 핵심이다.

### 3.2 워크플로우 구성

```
Webhook 노드 → IF 노드(만족도 ≤ 3) → true: Notion(Create a database page) → HTTP Request(Discord)
                                   → false: Notion(Create a database page)
```

**노드별 설정**

| 노드 | 설정 |
|---|---|
| Webhook | HTTP Method POST, Path 자동생성. Test URL / Production URL 두 종류 제공 |
| IF | 조건 `{{ $json.body.data.fields[1].value }}` / Number / is less than or equal to / `3` |
| Notion (true) | Create a database page, DB `/table`, 결과=`불만족 알림` |
| HTTP Request | POST, Discord 웹훅 URL, JSON Body |
| Notion (false) | Create a database page, DB `/table`, 결과=`정상` |

**Make와의 개념 대응**
- Make의 Router + 필터 2개 ↔ n8n의 **IF 노드 하나** (true/false 두 출구로 분기)
- Make의 HTTP 모듈 ↔ n8n의 **HTTP Request 노드**
- Make의 매핑 태그(클릭 삽입) ↔ n8n의 **expression** `{{ }}` 문법

**필드 매핑 (Tally 페이로드 기준)**
- 이름(Title): `{{ $('Webhook').item.json.body.data.fields[0].value }}`
- 만족도(number): `{{ $('Webhook').item.json.body.data.fields[1].value }}`
- 의견(rich text): `{{ $('Webhook').item.json.body.data.fields[2].value }}`
- 타임스탬프(date): `{{ $now }}`

> **중요한 차이 — 배열 인덱스 기준점**: 동일한 Tally 페이로드에서 만족도 필드가 Make에서는 `fields[2]`(1-베이스), n8n에서는 `fields[1]`(0-베이스)로 참조된다. 두 도구 간 이식 시 인덱스를 반드시 재확인해야 한다.

### 3.3 실행 결과

외부(Tally) 웹훅을 셀프호스팅 로컬로 직접 수신하려면 터널링(ngrok 등)이 필요하다. 본 검증에서는 Tally의 실제 페이로드와 **동일한 구조의 JSON을 curl로 전송**해 분기별로 검증했다. (클라우드인 Make는 이런 준비 없이 웹훅 URL이 즉시 공개 접근 가능하다는 점이 두 방식의 본질적 차이다.)

| 테스트 케이스 | 기대 동작 | 결과 |
|---|---|---|
| 만족도 2 전송 | IF true → Notion(불만족 알림) 기록 + Discord `[n8n]` 알림 | ✅ 통과 |
| 만족도 5 전송 | IF false → Notion(정상) 기록만, 알림 없음 | ✅ 통과 |

- Discord 알림에 `[n8n]` 태그를 붙여 Make 알림과 구분

### 3.4 구현 중 겪은 이슈와 해결 (n8n)

| 이슈 | 원인 | 해결 |
|---|---|---|
| Notion Database 목록이 비어 있음 | 통합 시크릿만 발급하고 페이지 접근 권한을 부여하지 않음 | 대상 DB 페이지 → `···` → 연결에서 n8n 통합 추가 |
| 배열 인덱스 불일치 | n8n은 0-베이스, Make는 1-베이스 | 만족도 참조를 `fields[1]`로 수정 |
| IF 이후 데이터 참조 혼동 | IF 노드 통과 후 `$json` 기준이 모호 | `$('Webhook')`으로 원본 노드를 명시 참조 |
| (잠재) 문자열/숫자 비교 실패 | Tally가 값을 문자열로 보낼 경우 Number 비교 실패 가능 | IF 노드의 "Convert types where required" 토글로 대응 가능 |

### 3.5 n8n 사용 소감 (장단점)

**장점**
- IF 노드 하나로 true/false 분기가 처리되어 분기 구조가 간결함
- expression `{{ }}`으로 데이터 참조가 자유롭고, `$('노드명')` 방식으로 임의 노드의 데이터를 명시적으로 가져올 수 있어 통제감이 높음
- 노드별 입출력 데이터(JSON)를 상세히 확인할 수 있어 디버깅이 편함
- 셀프호스팅이라 실행량 제한이 없음

**단점 / 주의점**
- 환경 구축(Docker)과 외부 서비스 연결(API 시크릿 수동 발급·권한 부여)에 초기 진입장벽이 있음
- 셀프호스팅은 외부 웹훅을 실제로 수신하려면 터널링이 추가로 필요함
- 배열 인덱스 0-베이스 등 세부 규칙을 알아야 하며, 노코드보다 개발 지식이 요구됨
- 호스트(노트북)가 꺼지면 워크플로우도 멈춤 — 상시 가동 워크플로우에는 별도 상시 서버가 필요

## 4. 비교 분석 (5개 항목)

> ⚠️ Make 열은 실제 구현 경험 기준으로 작성 완료. n8n 열은 구현 후 실제 경험으로 검증/보완할 것.

### 4.1 UI/UX

| | Make | n8n |
|---|---|---|
| 캔버스 방식 | 원형 모듈 + 시각적 흐름선. 분기(Router)가 그림으로 명확 | 사각 노드 그래프. IF 노드에서 true/false 두 갈래로 명확히 갈라짐 |
| 데이터 매핑 | 매핑 패널에서 클릭으로 태그 삽입. 직접 타이핑 불가 규칙 존재 | expression `{{ }}` 문법. 자유도 높고 미리보기로 값 즉시 확인 가능 |
| 체감 | 흐름 파악은 쉬우나 신구 모듈 혼재로 혼란 있었음 | 구조는 간결하나 expression·인덱스 등 개발 지식이 필요 |

### 4.2 설정 난이도

| | Make | n8n |
|---|---|---|
| 시작하기 | 웹 가입 즉시 사용. 설치 불필요 | Docker 컨테이너 실행 필요. 명령 한 줄이지만 Docker 환경이 전제 |
| 외부 서비스 연결 | Notion OAuth 클릭 몇 번으로 연결 완료 | Notion API 통합 생성 → 시크릿 발급 → 페이지 접근 권한 부여의 3단계 수동 진행 (검증 완료) |
| 함정 요소 | Legacy 모듈, Numeric/Text 연산자, 태그 vs 텍스트 | 페이지 권한 누락 시 DB 미표시, 0-베이스 인덱스, 외부 웹훅 수신에 터널링 필요 |

### 4.3 연동 서비스 범위

| | Make | n8n |
|---|---|---|
| 공식 커넥터 | 1,000개 이상 앱 모듈 | 500개 이상 노드. Notion은 Database/Page 등 액션이 세분화되어 제공 |
| 커스텀 연동 | HTTP 모듈로 임의 API 호출 가능 (Discord 웹훅에 사용) | HTTP Request 노드로 Discord 웹훅 호출 확인. Code 노드로 임의 로직 추가 가능 |

### 4.4 무료 플랜 범위

| | Make | n8n |
|---|---|---|
| 무료 조건 | 월 1,000 Ops (클라우드) | 셀프호스팅 시 실행 무제한, 비용은 컴퓨팅 자원만. 클라우드는 14일 트라이얼 후 유료 |
| 체감 | 웹훅 트리거 사용 시 제출 건당만 소모되어 여유 있음 | 실행 횟수 제한이 없어 부담 없으나, 호스트가 켜져 있어야만 동작 |

### 4.5 실행 로그 확인 방식

| | Make | n8n |
|---|---|---|
| 로그 위치 | 시나리오 History 탭 | Executions 탭 |
| 상세도 | 실행별로 각 모듈의 입출력 데이터 확인 가능. 캔버스에 실행 뱃지 표시 | 노드별 입출력 JSON을 Schema/Table/JSON 뷰로 상세 확인. 각 노드 실행 여부가 캔버스에 표시 |

## 5. 종합: 각 도구의 장단점 및 적합 상황

### 5.1 장단점 요약

| | Make | n8n |
|---|---|---|
| 장점 | 설치·가입 즉시 사용, OAuth 간편 연동, 시각적 흐름 직관적, 운영 편의 기능(큐/History) | 실행량 무제한(셀프호스팅), expression 자유도, 노드별 상세 디버깅, IF 분기 간결 |
| 단점 | 무료 Ops 한도, 신구 모듈 혼재, UI 잦은 변경 | 초기 구축·연동 진입장벽, 외부 웹훅에 터널링 필요, 개발 지식 요구, 호스트 상시 가동 필요 |

### 5.2 어떤 상황에서 어떤 도구가 적합한가 (의견)

두 도구를 동일 워크플로우로 직접 구현한 경험을 바탕으로, 상황별 적합성은 다음과 같이 판단한다.

- **Make가 적합한 경우**: 설치 없이 빠르게 시작하고 싶을 때, 비개발자이거나 소규모 자동화일 때, OAuth 기반 간편 연동이 중요할 때, 그리고 **항상 켜져 있어야 하는 스케줄·상시 워크플로우**일 때(클라우드라 기기 상태와 무관하게 동작). 실제로 프로젝트 2의 환율 스케줄 자동화에 Make를 선택한 이유가 이것이다.
- **n8n이 적합한 경우**: 실행량이 많아 무료 무제한이 필요할 때, 데이터 주권·보안상 셀프호스팅이 필요할 때, expression·Code 노드로 세밀한 커스텀 로직이 필요할 때, 그리고 개발 리소스가 있어 초기 구축 비용을 감수할 수 있을 때.

정리하면, **"빠르고 항상 켜져 있어야 하는 자동화"에는 Make, "통제권과 확장성·무제한 실행이 필요한 자동화"에는 n8n**이 적합하다.
