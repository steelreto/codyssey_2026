# [프로젝트 2] 자유 주제 자동화 설계 및 구현 — 환율 데이터 자동 수집·기록·임계값 알림

> 작성 상태: 설계 및 구현 완료

---

## 1. 자동화할 반복 업무 정의

**업무**: 원/달러 환율(USD/KRW)을 주기적으로 확인해 기록하고, 특정 기준을 넘으면 알림을 받는 일

**수동으로 할 때의 문제**
- 환율 사이트에 접속해 값을 확인하고, 어딘가에 기록하고, 기준 초과 여부를 판단해 전달하는 과정을 매번 반복해야 함
- 주기적으로 반복해야 의미가 있는데 사람이 하면 잊거나 누락되며, 특히 야간·주말에는 사실상 불가능
- 기록이 끊기면 시계열 데이터로서의 가치가 사라짐

**자동화 후 기대 효과**
- 사람 개입 없이 6시간마다 정확히 수집·기록 (24시간 무중단)
- 임계값(1,430원)을 넘을 때만 알림 → 평소에는 조용하고, 확인이 필요한 순간에만 통보
- Notion에 시계열 데이터가 자동 축적되어 추이 확인 가능

## 2. 도구 선정 및 이유

**선정 도구**: Make

**선정 이유**

프로젝트 1에서 Make와 n8n을 모두 직접 구현해본 경험을 근거로 Make를 선택했다.

1. **상시 가동이 필수인 트리거 특성** — 이 워크플로우의 핵심은 스케줄(시간 기반) 트리거다. 스케줄 트리거는 실행 환경이 항상 켜져 있어야 의미가 있다. 셀프호스팅 n8n은 노트북(호스트)이 꺼지면 워크플로우도 멈추지만, Make는 클라우드에서 실행되므로 사용자의 기기 상태와 무관하게 24시간 자동 실행된다. "Trigger 발생 시 자동 실행"이라는 요구사항을 실행 환경 측면에서 가장 확실히 충족한다.
2. **검증된 모듈 재사용** — 프로젝트 1에서 Make의 HTTP 모듈과 Notion 모듈을 이미 구현·검증했으므로 재현 리스크가 낮고 구현 속도가 빨랐다.
3. **무료 범위 내 운영 가능** — 실행 주기를 6시간으로 설정해 무료 플랜 한도 내에서 운영한다(3.4절 Ops 계산 참고).

## 3. 워크플로우 설계

### 3.1 전체 흐름

```
[Trigger] 스케줄 (매 6시간)
    │
    ▼
[Action 1] HTTP GET — 환율 API 호출 (Frankfurter, USD→KRW)
    │
    ▼
[Action 2] Notion 데이터베이스에 기록 (매 실행: 기록명, 환율, 수집시각)
    │
    ▼
[조건 분기] 환율 ≥ 1,430원?
    │
    ├─ 예 → [Action 3] Discord 알림 발송
    │
    └─ 아니오 → 종료 (기록만 남김)
```

### 3.2 요구사항 충족 매핑

| 과제 요구사항 | 구현 내용 |
|---|---|
| 자동화할 반복 업무 1개 정의 | 환율 확인·기록·기준 초과 알림 (1장) |
| 도구 1개 선정 및 이유 | Make 선정, 근거 서술 (2장) |
| Trigger 발생 시 자동 실행 | 스케줄 트리거(6시간) — Scheduling ON으로 무개입 자동 실행 |
| Trigger 1개 이상 | 스케줄 트리거 |
| Action 2개 이상 | HTTP(API 호출), Notion 기록, Discord 알림 (총 3개) |
| 조건 분기 1개 이상 | 임계값(1,430) 초과 여부 필터 |
| 각 분기 경로 1회 이상 실행 확인 | 초과/미초과 각각 실행 검증 완료 (4.2절) |
| 워크플로우 흐름 설명 | 3.1 다이어그램 + 3.3 단계별 설명 |

### 3.3 단계별 상세 설계 및 구현

**① Trigger — 스케줄**
- 주기: 매 6시간 (Make 좌하단 스케줄 설정에서 "Every 6 hours", Scheduling 토글 ON)
- 시간 기반 트리거로, 외부 이벤트 없이도 자동 실행된다. 프로젝트 1의 웹훅 트리거(이벤트 기반)와 대비되는 방식으로, "Trigger 발생 시 자동 실행" 요건을 가장 순수하게 충족한다.

**② Action 1 — 환율 API 호출 (HTTP 모듈)**
- 모듈: HTTP – Make a request
- URL: `https://api.frankfurter.dev/v1/latest?base=USD&symbols=KRW`
- Method: GET / Authentication: No authentication / Parse response: Yes
- Frankfurter는 API 키가 필요 없는 공개 환율 API로, 민감정보 노출 리스크를 원천 제거한다.
- 응답 구조에서 환율 값은 `data.rates.KRW` 경로에 위치한다. 실행 결과 statusCode 200으로 정상 응답을 확인했다(실측값 약 1,452원).

**③ Action 2 — Notion 기록**
- 모듈: Notion – Create a Data Source Item
- 전용 데이터베이스 `/환율` 신규 생성 (프로젝트 1 DB와 분리)
- 속성 및 매핑:

| 속성 | 타입 | 값 |
|---|---|---|
| 기록명 | 제목 | `USD/KRW` + `now` 함수 |
| 환율 | 숫자 | HTTP 모듈의 `data.rates.KRW` |
| 수집시각 | 날짜 | `now` 함수 |

- 임계값과 무관하게 매 실행마다 기록되어, 알림 발송 여부와 별개로 완전한 시계열 데이터가 축적된다.

**④ 조건 분기 — 임계값 필터**
- Notion 모듈과 Discord 모듈 사이에 필터 설정
- Label: `임계값 초과`
- 조건: `data.rates.KRW` / **Numeric operators: Greater than or equal to** / `1430`
- 숫자 비교이므로 반드시 Numeric 연산자를 사용했다(텍스트 연산자 사용 시 문자열 비교 오류 발생 — 프로젝트 1에서 학습한 원칙 적용).

**⑤ Action 3 — Discord 알림**
- 모듈: HTTP – Make a request (No authentication, POST, application/json)
- 임계값 초과 시에만 발송
- Body: `{"content": "[P2] 환율 알림: USD/KRW {환율}원 - 임계값(1430) 초과"}` (환율은 `data.rates.KRW` 매핑)

### 3.4 무료 플랜(Ops) 계산

- 매 6시간 실행 = 하루 4회 × 30일 = 월 약 120회 실행
- 실행당 모듈 3~4개(HTTP + Notion + 조건부 HTTP) → 월 약 480 Ops
- Make 무료 한도(월 1,000 Ops) 내에서 여유 있게 운영 가능
- (참고: 매 1시간 실행로 설계했다면 월 2,000 Ops 이상으로 무료 한도를 초과하므로, 주기를 6시간으로 조정한 것이 과금 리스크 완화의 핵심 결정이었다.)

### 3.5 알림 설계 원칙 — 예외 기반(Exception-based)

알림은 임계값을 초과할 때만 발송하도록 설계했다. 매 실행마다 알림을 보내면 알림 피로(alert fatigue)를 유발해 정작 중요한 경고를 놓치게 되기 때문이다. 평상시에는 Notion에 조용히 기록만 축적하고, 사용자가 개입해야 하는 예외 상황(임계값 초과)에만 알림으로 통보한다. 실행 자체의 정상 여부는 Notion에 쌓이는 기록으로 확인할 수 있다.

### 4.3 구현 중 겪은 이슈와 해결

| 이슈 | 원인 | 해결 |
|---|---|---|
| Discord Body `Unterminated string in JSON` 오류 | JSON 문자열 안에 이모지·특수문자가 포함되어 파싱 실패 | 이모지 제거 및 일반 문자로 정리 후 정상 전송 (JSON 형식을 단순화해 원인 격리) |
| `now`를 텍스트로 입력 시 날짜 오류 | 함수가 아닌 일반 텍스트로 인식됨 | 매핑 패널의 Date/Time에서 now 함수 태그로 삽입 (프로젝트 1과 동일 원칙) |
| 환율 값 매핑 위치 혼동 | Notion 모듈 출력에는 환율 원본이 없음 | 환율 원본을 가진 HTTP 모듈의 `data.rates.KRW`를 매핑 |

## 5. (선택) 보너스 과제

미채택. 핵심 요구사항(트리거·액션·분기·자동 실행)을 우선 완성하는 데 집중했다. 확장 방향은 다음과 같다.
- 보너스 1(AI Action): 알림 발송 전 AI로 "전일 대비 변동 요약 문구"를 생성해 알림에 첨부
- 보너스 2(실패 알림/재시도): API 호출 실패 시 에러 핸들러로 실패 알림 발송 및 재시도 경로 구성

## 6. 보안 및 제약 사항 준수

- API 키가 불필요한 공개 API(Frankfurter)를 사용해 민감정보 노출 리스크를 원천 제거
- Discord 웹훅 URL, Notion Data Source ID, 계정 이메일은 스크린샷에서 마스킹 처리 `[제출 전 최종 확인]`
- 전 과정 무료 범위 내 구현 (Make 무료 Ops, Frankfurter 무료, Notion/Discord 무료)
- 실행 주기를 6시간으로 설정해 무료 Ops 한도 내 운영 (과금 리스크 완화)
